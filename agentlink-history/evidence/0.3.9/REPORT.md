# 0.3.9：B 第 3 轮调用链核对、实际修复与结果

采纳 B 关于进程查询、清理调用链、串行化及源码身份的全部核对要求。检查发现真实的准入缺口后实施修改，不是仅为评审增加版本。A 确认本轮发现的代码修改和本机验证完成；尚无 B 对新修改的审查结论，完整双机验收未完成。

## 新发现和修复

0.3.8 的 ProcessJob.close 在查询/终止/关闭失败时保留句柄，本机 cleanup_pending 拦截也有效。但 run_initiator 的 finally 仍释放 discussion.lease；失败场次已为终态时，对端 _admit_start 可获准创建另一场次。本机服务路径注入 cleanup_pending 后复现，baseline-corrected.json 为 FAIL。该探针只证明“获准进入队列”，没有声称其本身发送了第二次模型请求。

0.3.9 添加独立 execution.lease，覆盖 _perform；任何清理未完成时保留该锁，成功清理后释放。双方准入和发起执行再次检查该锁。disconnect 按 client.close → 执行锁 → 角色锁顺序释放；清理失败抛错，不执行后续释放。已取消/失败的终态不变，同时仍向 UI 发送清理错误。新协议能力 agentlink-execution-lease-v3 要求双方支持，旧版混用的历史失败不改判。

最初探针的模拟节点未设在线状态，被能力检查提前拒绝，不能用作缺陷反证；纠正为在线对照后才获得上述 FAIL。原 probe 的一次测试输出误落入旧交付源码快照的 test-output，已移到 initial-probe-evidence；旧归档 ZIP 和受封存的源码文件未改，后续全部测试改在独立副本运行。

## 调用关系和新证据

GUI 的 command() 将停止/断开排队，stop() 仅设置 shutdown 事件。NodeService.run 所在线程处理命令、执行任务并在 finally 中 disconnect；RpcClient._reader 仅写日志和入队。正常产品路径中，每个 RpcClient 的清理由所属服务线程串行调用；没有宣称这些内部方法支持任意外部线程并发调用。

active_processes 使用 QueryInformationJobObject 返回值判断错误，失败抛 WinError，不能当作零活动进程。完整函数、完整 start/run_turn/close、准入与锁释放函数、GUI 退出函数、查询失败测试及两个新端到端测试，均直接按 AST 提取到 B-CALLCHAIN-REVIEW.md，附源码哈希，不是伪代码。0.3.8-to-0.3.9.diff 提供完整修改。

两个新增离线端到端用例分别在发起端 A、接收端 B 注入 TerminateJobObject 失败，确认实际模拟服务仍存活、原句柄仍保留、角色锁和共享执行锁仍持有、双方新请求被拒绝且不创建新场次。解除注入后通过命令队列再次断开，确认原服务退出及锁释放，再连接并完成新场次，恰好 A→B→A 三次模拟请求。清理记录的线程 ID 均为所属 NodeService 线程。原查询失败测试同时验证原始 OSError cause、send 未调用及错误事件。
