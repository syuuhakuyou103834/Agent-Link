# AgentLink 版本交付与开发日志规范

生效日期：2026-09-12。

用户明确要求：**从现在开始，每次交付新版本，都完整提供交付报告和开发 log。** 该要求长期适用于后续版本，首次覆盖计划中的 0.3.17。这里登记的是后续交付要求，不伪造此前版本缺失的开发历史。

业务需求主文件：[BUSINESS-REQUIREMENTS.md](BUSINESS-REQUIREMENTS.md)。

## 交付文件与位置

沿用 `C:\AgentLink-GUI\dist` 的发布形式。每版至少提供：

```text
C:\AgentLink-GUI\dist\
  AgentLink-GUI-<版本>\
    AgentLink.exe
    source\                         源码、测试、构建脚本及对应业务需求
    RELEASE-<版本>.md                完整交付报告
    DEVELOPMENT-LOG-<版本>.md        完整开发日志
    （既有运行时、许可证和说明文件）
  AgentLink-GUI-<版本>-Windows-x64.zip
  RELEASE-<版本>.md
  DEVELOPMENT-LOG-<版本>.md
  SHA256SUMS-<版本>.txt
  VERIFICATION-<版本>.json
```

- 报告和开发日志同时置于发布目录／ZIP 内，并在 dist 顶层提供独立副本，方便查看与传递给 B。
- 报告必须标明该版业务需求及验收状态，并附带相应需求文档；不能只提供 EXE 或 ZIP 链接。
- 完整机器日志或大量测试证据可单独打包，报告和开发日志必须提供索引及位置；明确哪些文件随包提供、哪些仅保留原机。
- 需要安装器时另附版本化安装包；未生成或未验证的交付物不得列为已完成。
- 保留旧版本和原始审查快照，不覆盖历史版本冒充新发布。发布编号、GUI、EXE 元数据、源码和文件名应一致。

## 交付报告 RELEASE-<版本>.md

每次交付完整填写以下内容；不适用项明确写“不适用”，未执行项写“未执行／阻塞”，不得省略造成误解。

1. **版本与来源**：发布日期、基线版本、受测源码路径、提交号或源码清单哈希、构建来源。
2. **业务范围**：对应需求编号、此次目标、实际完成项、未完成项，以及范围变更的用户确认记录。
3. **变化说明**：新增、恢复、修复、行为变化和删除的功能；没有删除时明确说明，不隐瞒回退。
4. **逐项验证**：用例／脚本、命令、环境、预期与实际、最终结果和证据链接；失败和未执行项单列。
5. **证据分层**：分别报告本机单元／模拟、真实 SMB、真实双机、真实模型、GUI、打包启动和安装升级验证，不相互替代。
6. **计数口径**：区分唯一测试用例和复跑次数；区分正式对话轮数、实际模型请求、失败尝试与模拟请求。
7. **已知限制**：遗留缺陷、未验证事项、环境阻塞、分歧，以及下一步需要谁执行什么验证。
8. **交付清单**：便携程序、ZIP、源码、测试、需求文档、报告、开发日志和证据的位置；提供校验清单及校验结果。
9. **升级与使用**：两端版本要求、启动方式、工作目录、设置／历史兼容和必要迁移；回退方法及限制只陈述已验证内容。
10. **发布结论**：区分构建完成、本机检查通过、已传给 B、B 独立验证、完整验收。没有证据不得宣称完成对应阶段。

ZIP 中的报告不嵌入自身最终 ZIP 哈希，避免循环依赖；最终 ZIP 哈希由外部 SHA256SUMS 和 VERIFICATION 文件记录。目录与 ZIP 内报告应一致。

## 开发日志 DEVELOPMENT-LOG-<版本>.md

从该版本开发开始记录，按实际时间持续追加；交付时必须提供完整可查阅版本。记录公开的工程行动、依据和证据，不包含模型内部思维链、账号凭据或无关个人数据。

每条记录至少包含：

| 字段 | 内容 |
|---|---|
| 时间 | 日期、时间及所在时区；不确定时明确标注，不补造准确时间。 |
| 阶段／需求 | 对应业务需求或缺陷编号；阶段如复现、修改、验证、打包、发布。 |
| 执行者与环境 | A／B／本机、运行环境；区分独立 B 复核和本机模拟 B。 |
| 起因与发现 | 用户要求、实际错误、观察结果、已确认原因及仍待核实的假设。 |
| 改动 | 修改哪些文件／行为，为什么；必要时链接差异或提交。 |
| 验证 | 精确命令或脚本、结果、首次失败、修复后结果、证据路径。 |
| 状态与下一步 | 完成／失败／阻塞／未执行；风险、未验证事项和后续处理。 |

日志必须覆盖：

- 初始基线和原始审查快照的保留、核验。
- 每项缺陷／需求的复现、实现和验证，不以最终总结替代开发过程。
- 方案调整、失败尝试、测试夹具修正，以及产品／测试／环境原因的区分。
- 中断和恢复：停止位置、已有成果、恢复依据、是否新增请求。
- 需求范围发生改变时的用户决定。
- 构建、版本号检查、GUI／启动检查、文件校验和实际发布结果。

首次失败和后续成功均保留，不能覆盖原日志制造“一次通过”。历史材料无法核实时标注来源与未知项。开发日志可链接大量原始输出，但自身应完整说明发生了什么及结论的依据。

## 发布前核对

- 业务需求、代码、测试、报告与开发日志指向同一版本及同一源码基线。
- 原始审查快照未改；修复后源码另有清单或版本记录。
- 报告和开发日志实际存在于交付目录／ZIP，链接有效，UTF-8 可读。
- 核对版本标识、ZIP 完整性、源码对应关系及 SHA-256。
- 对公开或跨机交付的材料检查凭据与无关个人数据；脱敏时说明证据边界并保留受控原件。
- 最终答复明确给出程序／ZIP、交付报告、开发日志链接，以及关键结果和未验证事项。

## 最终答复参考格式

```text
已交付 <版本>：<主要改进>。
程序／ZIP：<链接>
交付报告：<链接>
开发日志：<链接>
验证：<准确的结果和证据范围>
未验证／阻塞：<仍需处理的事项>
```

本规范是用户要求的交付质量约定，不替代具体任务的授权，也不要求每次交付前额外增加未被用户要求的审批环节。
